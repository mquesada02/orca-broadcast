# Research: how an Orca coordinator behaves when its workers stop (ticket #5)

Part of #2. Method: Orca docs and `--help` text only, plus live read-only output taken on 2026-10-05. Nothing was sent to, interrupted or closed on any terminal; no state-changing orchestration command was run.

Source tags: [S] `orca-ide skills get orchestration`; [S:<name>] `... --reference references/<name>.md`; [H:<cmd>] `orca-ide orchestration <cmd> --help`; [OC] `orca-ide skills get orca-cli`; [AC] `orca-ide agent-context`; [L:<cmd>] live output.

## Direct answer

1. **Workers stop after a pause message: nothing happens automatically.** The wait does not escalate, re-dispatch, or fail anything on its own. Orca's documented rule is that a timeout or empty `check --wait` is "a checkpoint, not a failure", and the coordinator must not stop, retry, release or relaunch without positive proof of exit [S]. A worker that is merely idle or waiting for CONTINUE shows as `live`, so the coordinator keeps waiting indefinitely in rolling waits. A Task only becomes `failed`/`stopped` via an explicit `worker_done --outcome failed`, an explicit `worker-stop`/`worker-abandon`, or circuit-break after three consecutive failed attempts, all of which need a prior failure or a coordinator action [S:recovery-and-cleanup]. A pause (agent alive, idle) is none of those. Caveat: after three consecutive empty waits the coordinator is told to enumerate with `worker-list` (not to act blindly) [S]; that is a model-driven step, not an Orca timer. No Orca-enforced worker timeout or auto-redispatch was found in any help text or reference (absence in the docs; I cannot read Orca source).
2. **Can a blocked coordinator receive `terminal send`?** The Orca side accepts it: `terminal send` writes to the PTY of any live writable terminal, and the coordinator's terminal listed `connected: true, writable: true` [L:terminal list]. Receipts report `input_accepted` and, only if the agent starts a turn, `turn_started`; "accepted: true proves input acceptance, not a started turn" [OC]. Whether the text is queued until the blocking `check --wait` returns is **unverified**: it depends on Claude Code's behavior while a Bash tool call is running (not documented in Orca sources), and I deliberately did not test it on a live coordinator. Orca itself relies on the same mechanism for workers: live workers in state `working` show the injected prompt "You have 1 orchestration message. Run `orca orchestration check`." [L:worktree ps]. Safer alternative documented by Orca: `orchestration send --to run:<id>` is a durable enqueue (wake/nudge best effort) [S][H:send]; but a Run group excludes its owning coordinator, and the coordinator reads that mail via `check`, so this channel is worker-to-coordinator, not coordinator-to-worker. For coordinator-to-worker pause use `send --to dispatch:<id>` or `@all` (group mail to every live Dispatch of the sender's Run) [H:send][S:messaging-and-gates], which a worker only sees when it runs `check` at a checkpoint [S:worker-contract]: it "does not interrupt you".
3. **How a coordinator shows in `worktree ps --json`.** The coordinator Claude agent appears as a normal agent row (`state` working/done, `agentType: claude`) under the worktree where its terminal actually lives, matched by `paneKey` = the terminal's `tabId:leafId`. Examples [L]: Run `run_<A>` (project A) has `coordinator_handle` `term_<A>`; that terminal is in the project A MAIN checkout (`~/Documents/Projects/<project-a>`, branch main, `agentIdentity: claude`), and `worktree ps` lists in that main-checkout row one agent, `working`, tool `Bash`, `paneKey <tabId>:<leafId>`, equal to that terminal's tab and leaf and to `sender_pane_key` on its sent messages. Three worktrees with coordinator names (such as `<name>-coordinator`) hold only a plain shell (`agentIdentity: None`, `agents: []`), so they list no agents. Same for project B: Run `run_<B>` coordinator is the agent in the project B main checkout (`working`, `Bash`). So "coordinators with no agents" are named worktrees that are not where the coordinator agent runs. Exception seen: one coordinator-named worktree has an agent in `done` state (a coordinator-named worktree that does hold a Claude).
   - While blocked in `check --wait`, the coordinator's agent state stays `working` (a tool call is running), not `waiting` or `done` [L]. So a naive "pause every working agent" will also pick up coordinators, and a pause message typed into a coordinator would be the same terminal-input question as point 2.
4. **Orchestration-level pause/hold of a Run or Dispatch: none exists.** The commands are run-create/use/current/list/show, send, check, reply, inbox, task-*, worker-start/show/read/stop/abandon/release/retain/list, dispatch, request-show, dispatch-show, ask, gate-*, reset [H:orchestration]. A Run has only id, objective, coordinator_handle, consumer_generation, legacy, timestamps: no status field [L:run-show]. "A Run is a durable namespace and coordinator inbox; it does not schedule or place workers" [S]. `task-update` statuses are pending, ready, dispatched, completed, failed, blocked [H:task-update]; `blocked` is a Task status the coordinator could set, but nothing in the docs says it halts a running Dispatch (unverified; and it is a mutating command). Closest primitives: `gate-create` is a coordinator-owned decision blocking a Task in the DAG, not a worker pause [S:messaging-and-gates]; `worker-stop` fences and closes the agent terminal (destructive, not a pause) [S:recovery-and-cleanup]; `worker-abandon` fences without stopping, losing authority. No "pause" or "hold" for Runs appears in `agent-context` (its only "pause" hit is browser request interception) [AC]. The orca-cli docs offer workspace Sleep for resumable sessions, but ticket #2 marks it out of scope and it is not scriptable here.

## Evidence

### Waits and timeouts
- `check --wait` blocks until a matching message arrives or `--timeout-ms` expires; emits `_keepalive` JSON lines on stderr every 15s [H:check]. `--types` is only the wake condition; the Delivery is the whole FIFO batch, replayed until `--ack` [H:check][S:messaging-and-gates].
- Canonical loop: `check --wait --types "worker_done,escalation,question" --timeout-ms 900000`; "Keep waiting until every expected Dispatch settles. A timeout or empty result is a checkpoint, not a failure." [S]
- After three consecutive empty waits: enumerate with `worker-list --include-remote --json` and act on `projection.attention`, `requiresAction`, literal `nextAction`; `none` means keep waiting [S].
- Stop/abandon only on positive proof: `exited` liveness, the worker's own observation of process exit, or a transcript whose final agent turn sent no `worker_done`. `unverifiable` "is absence" and never authorizes stop, abandon, retry or release [S][S:recovery-and-cleanup].
- A paused-but-alive Claude: `worker-list` row `liveness.verdict: live`, `source: agent_status`, `nextAction: none`, `attention.requiresAction: false` [L:worker-list run_<A>]. `worker-show` `observation.agentWait` reports a worker parked on a human-only prompt and "A waiting worker is healthy, not failed" [H:worker-show]. A paused worker waiting for CONTINUE is probably neither; `agentWait` would be null (unverified).
- Layered liveness: `worker-list projection.liveness` is the fleet verdict; `worker-show observation.status` is PTY liveness only; "A live terminal can still hold a dead or stuck agent." [S]
- Failed/stopped attempts are retried by the coordinator with `worker-start --task <id> --retry-of <dispatch>`; after three consecutive failures the Task circuit-breaks to failed [S:recovery-and-cleanup]. Retry is only for positively proven failed/stopped attempts.
- Worker side: heartbeats are skipped while blocked in `ask` or `check --wait`; those calls are the liveness signals [S:worker-contract]. No heartbeat-timeout reaping is documented (not found).

### Messages to workers and coordinator
- `send` success proves durable enqueue only; wake/nudge is best-effort and does not prove the recipient read it [S][S:messaging-and-gates].
- Follow-ups to a running worker "arrive" only when the worker runs `check` at checkpoints; enqueue "does not interrupt you" [S:worker-contract]. A pause message via orchestration therefore lands at the worker's next `check`, not mid-step.
- Group addresses `@all`, `@idle`, `@claude`, ... reach live Dispatches of the sender's Run; Run groups exclude the owning coordinator; `@worktree:<id>` reaches matching workspace terminals, including coordinators [H:send][S:messaging-and-gates].
- `check` on a bound Run returns the Run's inbox; a worker whose Dispatch is superseded gets `consumer_fenced` and must stop [S:worker-contract].
- Live inbox shows coordinator messages to `dispatch:<id>` with `read: 0`, `delivery_contract: current_delivery`, and a nudge fields set (`pointer_enter_pending`, `pointer_pty_id`) [L:inbox]; consistent with an Enter-pointer nudge typed into the worker PTY (inference, not documented).
- `terminal send` receipts: `input_accepted` then `turn_started`; default observe 0 s; `--wait-submit N` only observes; `--retry-request` for idempotent replay; older hosts fall back to `old-host` raw input [H:terminal send][OC].

### Coordinator identity
- `run-list` entries carry `coordinator_handle` (a `term_...`); `terminal list --json` has `worktreePath`, `tabId`, `leafId`, `agentIdentity`; `worktree ps --json` has `agents[].paneKey` (`<tabId>:<leafId>`) [L]. Joining on `tabId:leafId` identifies which agent row is the coordinator, per Run.
- Terminal list: 38 terminals; 6 in `*coord*` worktrees; only one of them has `agentIdentity: claude` [L:terminal list].
- Runs listed (live): about ten Runs from several projects [L:run-list]. Run `run_<A>`: tasks 14 completed, 3 dispatched [L:task-list]. Run `run_<B>` worker counts: active 3, retained 2, released 7 [L:worker-list].

## Implications for orca-pause (inputs to #2, not decisions)
- `pause` selecting "agents with state working" will include coordinators (state stays `working` while in `check --wait`, because a tool call is running). Distinguish coordinators by joining `run-list.coordinator_handle` to `terminal list` and then `tabId:leafId` to `paneKey`.
- Pausing only workers, leaving the coordinator blocked, is safe from Orca's view: waits are rolling checkpoints; paused-but-alive workers read `live`. Nothing auto-fails them. The risk is behavioral: the coordinator model might, after three empty waits, call `worker-list`; it should see `live` / `nextAction none` and keep waiting.
- Resume uses the same channel as pause for each agent; for coordinators, no Orca-level resume exists.
